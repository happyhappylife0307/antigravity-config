# 漫画LP完成ビルダー

Gemini Sparkで、商品・目的・決裁構造に合う販売ストーリーを選び、作画と検品を経て納品データまで作る。画像や検品が欠けた状態を「完成」と呼ばない。

## 最初に宣言する
「漫画LP完成ビルダーを使い、顧客変化設計→ストーリー選定→ネーム→キャラ参照3枚以上→全ページ作画→組版→四面品質審査→計測設計→ZIPまで進めます」と短く伝える。

## 1. 入力を確認する
`references/input-contract.md` と `references/marketing-brief.md` を読む。この2ファイルをマーケティング設計の正本とし、別の商品・スキルを前提にしない。添付、商品URL、既存原稿、ブランド資料を確認し、URLの事実を検証する。分からない仕様・効果・期限を補わない。

制作前に、ファネル、流入元、KPI、変化で定義したターゲット、利用者、決裁者、支払者、購入障壁、購入前、購入直後、商品体験後、非保証、根拠、計測と改善基準を `meta.marketing` に固定する。結果が大きく変わる不足だけ質問し、推定は `brief.json` に明記する。宣言なしにネームへ進まない。

## 2. 販売ルートを選ぶ
`references/modes.md` を読む。通常は `auto` で最大3案を理由つきで提示し、推奨案を知らせる。ユーザーが販売表現を指定した場合だけ手動選択する。選択結果は `route_decision` に記録する。

利用者と決裁者が別で、購入・申込が目的なら成長実感型を優先する。成長実感型は次を省かない。

1. 強い未解決フック
2. 現在の困りごと
3. 仲間・同世代の促し
4. 決裁者への相談
5. 商品との出会いと実体験
6. 目で分かる小さな成功
7. できるようになった行動で示す明るい未来
8. 根拠のある具体的CTA

採用した商品タイプ、目的、ターゲット、望ましい変化、主ストーリー、代替案、選定理由、販売圧をユーザーへ知らせる。

## 3. ジョブを初期化する

この `SKILL.md` があるフォルダをスキルディレクトリとして扱う。Mac版Sparkでは、ユーザーが許可したConnected folder内に案件ごとの新しいジョブフォルダを作る。既存ファイルは確認なく上書き・削除しない。

```bash
python3 <skill-dir>/scripts/builder.py init <job-dir> \
  --title "商品名" --product knowledge --goal conversion \
  --style auto --separate-decision-maker
```

`brief.json` と `script.json` の仮文を確認済みの事実と自然な日本語へ置き換える。`未確定`、抽象的なターゲット、根拠のない変化、`example.com` を残さない。広告主自身の商品名と使用許諾を確認できた名称だけを `meta.rights.authorized_names` に登録する。第三者の企業名、商品・サービス名、ロゴ、キャラクター、特徴的な意匠を漫画本文・吹き出し・作画指示へ入れない。

## 4. ネームを作り、厳格検査する

`references/quality-gates.md` を読む。各ビートをマーケティング・ブリーフへ接続する。1ページ目はターゲットの具体的状況から未解決疑問を作る。購入目的は証拠ループを2組以上置き、最後は冒頭の象徴を反転し、証明可能な行動変化と具体的CTAを見せる。

```bash
python3 <skill-dir>/scripts/builder.py validate <job-dir>
```

エラー0になるまで原稿を直す。警告も内容を確認して解消または理由を記録する。

## 5. キャラ参照と全パネルを作画する

`references/image-workflow.md` を読む。

```bash
python3 <skill-dir>/scripts/builder.py prompts <job-dir>
```

`reports/image_jobs.json` の順番で、Gemini Sparkで利用可能な画像生成機能を使う。最初にキャラクター参照シートを最低3枚作り、次に全パネルを作る。各ジョブの参照画像、プロンプト、比率を渡し、PNGをConnected folder内の `target` へ保存する。

画像生成またはローカルファイル保存が利用できなければ停止し、プロンプト完成までであることを明記する。Web版・モバイル版でローカル工程を完走できない場合は、Mac版SparkとConnected folderで続行するよう案内する。プレースホルダーやデモ画像を納品しない。

```bash
python3 <skill-dir>/scripts/builder.py status <job-dir>
```

不足0まで続ける。全ページを目視し、人物、小道具、商品、手、顔、不要文字、吹き出し余白を確認する。問題画像だけ再生成する。

## 6. 四面品質審査を通す

`reports/audit.json` の `machine`、`style`、`fact`、`legal` を実検品する。各 `status` を `pass` にするだけでなく、何を見たか `evidence` に書く。

- 機械: strict検査、素材欠落、リンク、出力破損
- 文体: 読み順、キャラ一貫性、1ページ目のフック、最後の達成感
- 事実: 商品資料・一次情報との照合
- 法務: 誇大表現、期限、権利、未成年、第三者商標・ロゴ・キャラクター、必要注記

## 7. 完成データを作る

`references/output-contract.md` を読む。

```bash
python3 <skill-dir>/scripts/builder.py finalize <job-dir>
```

失敗したら不足を直して再実行する。`--allow-demo` は自己試験専用で、ユーザー案件には使わない。

完成後、`output/lp.html` を開き、ページ画像、CTA、注記、スマートフォン幅を確認する。ZIPの破損検査を行う。

## 8. 納品する

次を絶対パスのリンクで渡す。

- `output/manga-lp-delivery.zip`
- `output/lp.html`
- `output/note_vertical.png`
- `output/pages/`
- `reports/audit.json`

採用した販売ルート、厳格検査結果、残る注意点を短く添える。

## してはいけないこと

- 1ページ目を商品説明や自己紹介だけで始めない。未解決疑問を置く。
- 最後を「気になったら見てね」だけで終えない。目で分かる達成と具体的な未来を描く。
- 画像プロンプト、プレースホルダー、デモ素材だけを漫画LP完成品として渡さない。
- 商品にない機能、効果、実績、口コミ、期限を作らない。
- 広告主の商品名を除き、実在する第三者の企業名、商品・サービス名、ロゴ、キャラクター、特徴的な意匠を出さない。
- キャラクター参照を作る前に全パネルをばらばらに生成しない。

## 検収基準

次が全部揃ったときだけ「漫画LP完成」と言う。

- ネームの厳格検査がエラー0
- 成果設計カード、ターゲット、購入前後の変化、ルート比較、計測・改善基準が確定
- キャラ参照3枚以上と全パネル実画像
- キャラ一貫性の目視確認
- 四面品質審査が根拠付きで合格
- 権利台帳に広告主の許諾済み名称だけがあり、第三者標章なしの確認記録がある
- ページPNG、自己完結HTML、縦長PNG、SNSカード
- manifest付きで破損のない納品ZIP
